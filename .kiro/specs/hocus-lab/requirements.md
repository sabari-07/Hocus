# Requirements Document

Spec: hocus-lab

## Introduction

Hocus Lab is the set of developer tools that show why the engine decided what it did and turn sessions into
tests: the X-ray decision view, the timeline simulator, the session recorder with replay export and load, and
the replay corpus that runs in CI. It lives in `packages/devtools` (`XRay.tsx`, `Simulator.tsx`, `summary.ts`,
`index.ts`), the recorder parts of `packages/ui/src/runtime.ts`, `scripts/generate-replays.ts` and
`tests/replays/`. Every tool reads the same `DecisionRecord`s and event logs as the engine and the tests.

## Glossary

- **Decision record:** what the engine stored for one command: text, frame, samples, candidates with evidence parts, parameters, context and outcome (fusion-engine 7).
- **Session log:** every event dispatched in the current session (`HocusRuntime.log`).
- **Replay file:** a JSON file (`*.replay.json`) with `version`, `app`, `origin`, `description`, `lang`, `config`, `events` and an `expected` block.
- **Origin:** `synthetic` (generated by a script) or `recorded` (exported from a real session).
- **Live tuning:** re-resolving a stored record with other parameters, without side effects.

## Requirements

### Requirement 1: X-ray decision view

**User Story:** As a developer or a judge, I want to see what was pointed at, when each word was heard and how the candidates scored, so that I can trust and tune the engine.

#### Acceptance Criteria

1. WHEN the X-ray is open (top-bar button or the `X` key), THE SYSTEM SHALL show the selected decision (the latest by default) as three lanes over 2.6 s before to 0.6 s after the command: pointer segments coloured per object with opacity by stability, each timed word with its window and binding, and the top 4 candidates' evidence bars with the `minEvidence` line.
2. THE SYSTEM SHALL list the last 6 decisions as buttons marked by outcome, and selecting one SHALL show it.
3. WHEN the user moves the scrub slider, THE SYSTEM SHALL show the nearest pointer sample's hits with qualities, its source and its confidence at that time.
4. WHEN the user moves a tuning slider (window before, window after, ask margin, minimum evidence, stability speed, lag), THE SYSTEM SHALL re-resolve the record with `engine.reresolve` and show the new decision without changing the session; a lag change SHALL shift the word times of spoken commands by the difference.
5. WHEN the user clicks "Reset tuning", THE SYSTEM SHALL return to the recorded parameters.
6. THE SYSTEM SHALL give the lanes an `aria-label` and a polite live text, both from `summarize(resolution)`.

### Requirement 2: Recorder, export and load

**User Story:** As a developer, I want to save a real session and load it again, so that a bug seen once can be studied and kept.

#### Acceptance Criteria

1. THE runtime SHALL keep every dispatched event in the session log, dropping the oldest beyond 60,000 events, and the Recorder tab SHALL show the event count.
2. WHEN the user exports a replay, THE SYSTEM SHALL download `<app id>-<timestamp>.replay.json` with `version: 1`, `origin: "recorded"`, the language, `lagMs` and `minEvidence`, all logged events, and an `expected` block with each decision's text, outcome and (when resolved) bindings, plus the final app state.
3. WHEN the user loads a replay file, THE SYSTEM SHALL validate it with `parseReplayFile` (Zod), start from a fresh state in the file's language, dispatch its events in order and sync the scene.
4. WHEN the user clicks "Copy test" on a decision, THE SYSTEM SHALL copy a Vitest snippet (`testSnippet`) that replays a file and compares the text and outcome of every decision with `expected`.
5. IF a loaded file fails validation, THEN THE SYSTEM SHALL reject it and SHALL NOT replace the session.

### Requirement 3: Replay corpus

**User Story:** As a maintainer, I want saved sessions to run as tests, so that sessions must keep resolving the same way after every change.

#### Acceptance Criteria

1. THE SYSTEM SHALL keep replay files in `tests/replays/*.replay.json`, each validated by `parseReplayFile`.
2. WHEN `tests/replays/replays.test.ts` runs, THE SYSTEM SHALL fold every file through the real app's engine with the file's config and language, and SHALL require the decisions (text, outcome, bindings) and, when present, the final app state to equal the file's `expected` block.
3. IF a replay file names an app that is not registered in the test, THEN THE test SHALL fail.
4. WHEN `npm run replays:generate` runs, `scripts/generate-replays.ts` SHALL build synthetic sessions from scripted dwells and utterances through the real engine and write them with `origin: "synthetic"`.
5. THE generator SHALL NOT overwrite a file whose origin is `recorded`, and synthetic files SHALL never be labelled `recorded`.
6. THE corpus SHALL be readable by the `hocus-mcp` replay tool, which reports whether each file still matches.

### Requirement 4: Timeline simulator

**User Story:** As a developer without a camera, I want to build a pointer timeline and a sentence by hand, so that I can see how the resolver decides edge cases.

#### Acceptance Criteria

1. THE simulator SHALL let the user list pointer segments (target or nothing, duration, fast sweep or not), type an utterance and set the time of the first pointing word.
2. WHEN the user runs the simulation, THE SYSTEM SHALL build samples every 33 ms (60 px per sample for a fast sweep, 1 px jitter otherwise), parse the utterance with the app's parse context, set word times at t, t + 400 and t + 800 ms, and call `resolveFrame` with `DEFAULT_CONFIG`.
3. THE SYSTEM SHALL show the result status and the `summarize` text in a polite live region.
4. WHEN the utterance is a control phrase or is not understood, THE SYSTEM SHALL show `no_action` with the reason.
5. THE simulator SHALL NOT change the session state.
